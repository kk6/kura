# スパイク：ポーズの類似検索の骨格推定モデル（フェーズ3のタスク12）

使い捨てのプロトタイプです。本体のコードには使いません。

状態：利用者が並びを見て決めた（2026-11-18）。決めたことは最後の「決めたこと」と、要件定義書の5.6「ポーズ（3b）」にある。

## 確かめたいこと

1. 候補の構成（RTMPose-s、RTMPose-m、RTMO-s）で、似たポーズの並びに納得できるか
2. 複数人の扱い（一番大きい1人だけ、全員を持って一番近い組で比べる）
3. 左右反転したポーズを同じとみなすか
4. ポーズで読む画像（幅320pxのサムネイル、元の画像）
5. 人物なしと「人物はいるが、比べられる関節が足りない」の数（FR-605）
6. 1枚あたりの時間（Kura のワーカーと同じ1スレッド）と、モデルの大きさ

YOLO-Pose（AGPL-3.0）と MediaPipe（TFLite）は候補から外した（要件定義書の10章）。

## 試した方法

- 写真274枚を読み取り専用で使った。ドキュメント用の見本 `~/Projects/kura-library`（人物169、動物28、小物10、風景24）と、利用者が足した `~/Projects/kura-pose-extra`（43枚。寝る、膝を立てて座る、頭が写っていない胴体、極端なアングル、手だけなど）。本物の資料は使っていない
- `fetch.py`：OpenMMLab の公式の配布先から zip を取り、`.onnx` だけを `models/` に取り出す
- `pose.py`：サムネイルを本体と同じ条件（幅320px、JPEG 品質85）で `out/thumbs/` に作る。構成ごとに、サムネイルと元の画像の両方から骨格（COCO 17点）を推定し、時間を測る。前後処理は RTMLib 0.0.16 を使った
  - トップダウン（RTMPose-s / m）：YOLOX-tiny（入力416×416、人物の閾値0.7）で人物の枠を出し、枠ごとに RTMPose（入力 192×256）で関節を出す
  - 1段（RTMO-s）：入力640×640 で人物と関節をまとめて出す（閾値0.7）
  - ONNX Runtime は CPU、1スレッド（`intra_op_num_threads=1`）。RTMLib はセッションの設定を渡さないので、`InferenceSession` を差し替えて渡した
- `report.py`：類似度を計算し、統計を `out/stats.md` に、並びを見比べるページを `out/index.html` に出す

ポーズの類似度（試しに決めた方法。本体の仕様ではない）：

- 関節のスコアが 0.3 未満の点は「見えない」として比べない。見えている関節が6点未満の人物は比べない
- 2人の、共通に見えている関節だけを取り出し、重心を引いてから（位置をそろえる）コサイン類似度を取る（大きさをそろえる）。回転はそろえない（寝ている人と立っている人は似ていないとする）
- 共通の関節が少ない組が不当に高くならないよう、基準で見えている関節のうち比べられた割合を掛ける
- 複数人：「一番大きい1人だけ」は枠の面積が最大の人物だけを使う。「全員」は全ての組の最大を使う
- 左右反転を同じとみなすときは、反転した骨格（左右の関節を入れ替える）とも比べて大きい方を使う

### 1枚あたりの時間（1スレッド。最初の3枚を除く）

| 構成 | 読む画像 | 読み込み | 検出 | 骨格 | 全体（中央 / 平均 / p95） | 2万枚の見込み |
| --- | --- | --- | --- | --- | --- | --- |
| rtmpose-s | サムネイル | 0.7ms | 12.2ms | 8.3ms | 21 / 22 / 38ms | 約7分 |
| rtmpose-m | サムネイル | 0.7ms | 12.3ms | 17.5ms | 31 / 33 / 66ms | 約11分 |
| rtmo-s | サムネイル | 0.7ms | - | 65.3ms | 66 / 67 / 68ms | 約22分 |

- 2万枚の見込みは「2万 × 平均 ÷ 60,000 分」。274枚の構成に依存する外挿で、2万枚を流してはいない。内容（SigLIP 2、1スレッドで約17分）に加わる
- トップダウンの骨格の時間は人数に比例する（rtmpose-m で 1人 17.5ms、2人 35ms、3人 70ms）。RTMO は人数によらず約66ms
- 元の画像は読み込みが1枚 約125ms（4000万画素を超える8枚は全体で 300〜370ms）。時間の大半は推論ではなくデコード
- セッションの読み込みは 17〜28ms

人物の写真（人物と kura-pose-extra の212枚）で「ポーズあり」にならなかった画像：

- rtmpose-m・サムネイル：11枚。うち7枚は「関節が足りない」で、手だけの写真や胸元・胴体のアップ（ページで目で確かめた）。人物を見逃したのは4枚
- rtmpose-m・元の画像：18枚。サムネイルより多い。元の画像を 416×416 に縮める処理（OpenCV の線形補間）が、サムネイル（Pillow の BOX）より粗いためと推測している（確かめていない）
- rtmo-s・サムネイル：27枚。同じ人物が3回写った写真（多重露光）、倒立、手だけの写真などを「人物なし」にした
- 動物・小物・風景の62枚で人物が出たもの：rtmpose-m・サムネイルで7枚。写真に実際に人が写っているかは、ページの4番目の節で見る

### RTMLib について確かめたこと（0.0.16）

- 読み込み時に `print()` で `load … with onnxruntime backend` を出す。本体のワーカーで使うなら、stdout の JSONL を壊さないよう止める必要がある
- セッションの設定（スレッド数）を渡せない
- RTMPose は枠が空だと画像全体を1人として推定する。RTMO は人物がいないと全部0の1人分を返す。どちらも「人物なし」を見分けるには呼ぶ側の処理が要る（このスパイクでは `pose.py` で処理した）
- モデルのパスが存在しないとダウンロードを始める。このスパイクでは、先に置いたファイルのパスを渡した
- 依存に OpenCV（`opencv-python` と `opencv-contrib-python`。合わせて約138MB）が入る。ワーカーの大きさは測っていない。前後処理（拡大縮小、アフィン変換、NMS）を NumPy と Pillow で書き直せば、OpenCV は要らなくなる見込み

## 決めたこと（2026-11-18、利用者が並びを見て決めた）

1. 構成：rtmpose-m。rtmpose-s は並びの質で外した。rtmo-s は骨格を出せたときの精度は良く見えたが、人物が写っているのに「人物なし」になる画像があり、複数人の検出も甘かった
2. 複数人：全員を持ち、一番近い組で比べる
3. 左右反転：同じとみなす
4. 読む画像：サムネイル
5. 関節不足：ポーズは比べないが、「人物なし」と分けて記録する

あわせて決めたこと：比べる側の画像にポーズがないときは、ポーズの類似度を平均（そろえた後の0）とみなす。構図の特徴量は 3b では見直さない。ポーズのスライダーは「体の姿勢／手足や胴の向き」。
