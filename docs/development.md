# 開発ガイド（Claude Code への頼み方）

Claude Code の新しいセッションで Kura の開発を頼むときの、頼み方と確かめ方をまとめます。

Claude Code は、セッションの始めに [CLAUDE.md](../CLAUDE.md) を読みます。技術構成、コマンド、画面の決まり、データの扱いは CLAUDE.md に書いてあります。頼むときに繰り返す必要はありません。この文書には、CLAUDE.md に書いていない「何をどう頼むか」を書きます。

## 進め方

1. やることを1つ決める。`docs/tasks/phase<N>.md` のタスク1行か、`docs/requirements.md` の FR-xxx の ID 1つ（関連する数個まで）が単位です
2. 新しいセッションを開き、下の「頼み方の例」の形で頼む
3. Claude が計画や質問を返したら答える。要件定義書の「未決事項」に当たることは、Claude が実装で決めずに質問します
4. 実装と検証が終わったら、結果を確かめる（「終わったときに確かめること」）
5. 次のタスクは、また新しいセッションで頼む

1つのセッションでは1つのタスクだけを進めます。セッションが長くなると、前の作業の文脈が混ざります。

## 頼み方の例

### フェーズのタスク一覧を作る

フェーズ2の作業を始める前に、タスク一覧を作ります。

> docs/requirements.md の「開発フェーズと優先度」のフェーズ2を、docs/tasks/phase1.md と同じ形でタスクに分けて、docs/tasks/phase2.md に書いてください。未決事項に当たるものは、決める前に質問してください。

### タスクを進める

> docs/tasks/phase2.md のタスク3をやってください。ブランチを切って、終わったら PR を出してください。

「終わったと言える状態」はタスク一覧の列にあるので、書かなくてかまいません。タスク一覧にない作業なら、ID と終わったと言える状態を書きます。

> FR-106（最近使ったライブラリから、見つからないライブラリを外す）を作ってください。終わったと言える状態：選択画面で見つからないライブラリを外せて、ライブラリのフォルダは変わらない。

### 不具合を直す

現象、再現の手順、期待する動きを書きます。どのライブラリで起きたかも書きます。

> 試し用のライブラリで、カテゴリを2つ続けて移すと、2つ目のカテゴリの件数が0になります。手順：…。期待：件数は移す前と同じ。再現するテストを先に書いてから直してください。

本物の資料のライブラリで起きた不具合は、ファイル名やフォルダ構成を書き写さず、ダミーのライブラリで再現できる形に言い換えて伝えます。

### 画面を変える

> 詳細パネルの評価の星を、押したときにすぐ反映されるようにしてください。

Claude は `docs/design.md` を読み、モックの画面のスクリーンショットで見た目を確かめます（CLAUDE.md の「画面の決まり」）。見た目の好みがあれば、言葉か参考のスクリーンショットで伝えます。

### ドキュメントだけを直す

> docs/user-guide.md のゴミ箱の節を、今の画面に合わせて直してください。スクリーンショットも撮り直してください。

### リリースの準備をする

> v0.2.0 のリリースの準備をしてください。CHANGELOG にはフェーズ2でできるようになったことを書いてください。タグの push は自分でします。

手順は CLAUDE.md の「リリース」にあります。タグの push で GitHub Release ができるので、タグを push してよいかは頼むときにはっきり書きます。

## 検証を頼む

変えたものによって、確かめ方が違います。Claude はスキルの説明を見て自分で選ぶこともありますが、はっきり頼むと確実です。

| 変えたもの | 確かめ方 | 頼み方 |
| --- | --- | --- |
| 画面だけ（React） | モックの画面を Playwright で開き、スクリーンショットで見る（`npm run test:e2e`） | 「スクリーンショットで確かめてください」 |
| Rust のコマンド、取り込み、DB、ファイル操作 | 実アプリを隔離して起動し、操作して、画面・ファイル・DB で確かめる | 「/verify-kura で実アプリで確かめてください」 |
| 移動の手順（`fileops.rs`、`library.rs` の `connect` と `apply_op`、`pending_ops`） | 途中で落ちても画像を失わないことを TLA+ のモデル検査で確かめる | 「/verify-crash-safe-move を流してください」 |

### /verify-kura（実アプリでの確認）

- 中身は `.claude/skills/verify-kura/` にあります。機能ごとの手順は `features/` にあります
- デバッグ版の `Kura.app` を、利用者のアプリのデータ（最近使ったライブラリなど）から切り離して起動します。本物の資料のライブラリは開きません
- Kura の画面のボタンを押すには、画面全体の操作が要ります。Claude が許可を求めたら承認します。操作の間はマウスとキーボードを使わないでください
- 証跡（スクリーンショット、DB の結果、ログ）は `.claude/tmp/verify-kura/runs/<run の名前>/evidence/` に残ります

### /verify-crash-safe-move（移動の手順のモデル検査）

- 中身は `.claude/skills/verify-crash-safe-move/` にあります。約5秒で終わります
- 初回は Java と TLC（`tla2tools.jar`）が要ります。置き方は SKILL.md の「準備」にあります
- `DRIFT` が出たら、モデルが写しているコードが変わったという意味です。Claude はコードを読み、モデルを合わせ直してから検査を流します
- `FAIL` が出て、反例がコードで実際に起こりうるものなら、本物の不具合です。Claude は性質を緩めて通さずに、反例を報告します

### スキルを最新に保つ

アプリが変わると、スキルの手順が古くなります。次のように頼みます。

- 実アプリの確認の手順：「/pstack:maintain-verification-skill で verify-kura を今のアプリに合わせてください」
- モデル検査：「/pstack:maintain-formal-verification-skill で verify-crash-safe-move を今のコードに合わせてください」

## 頼むときに伝えるとよいこと

- 対象の ID（FR-xxx、NFR-xx）か、タスクの番号
- どこまで進めるか。手元の変更まで、コミットまで、PR まで、のどれか。Claude は頼まれないとコミットも push もしません
- 範囲の外にすること（「カテゴリの色はこのタスクではやらない」など）
- 決まっていて文書にないこと。決めたことは、Claude に `docs/requirements.md` へ書き戻してもらいます

## 終わったときに確かめること

- PR の説明に、対応した ID が書いてある
- CI が通っている（web、e2e、rust、python）
- 画面を変えたなら、スクリーンショットを見る。実アプリで確かめたなら、証跡を見る
- 画面の動きや文言を変えたなら、`docs/user-guide.md` も直っている
- 決めたことが `docs/requirements.md` に書き戻されている

## 本物の資料について

- Claude は本物の資料フォルダに触れません。これは CLAUDE.md の決まりとして守るもので、設定で全部を防いでいるわけではありません
- `.claude/settings.json` が禁じているのは、`~/Pictures/References/` の下を Read と Edit のツールで読み書きすることだけです。Bash のコマンドからの読み取りや、ほかの場所にある資料フォルダは防げません。資料フォルダの場所をセッションの中で伝えないでください
- 本物の資料での確認は、利用者が自分で行います。手順は `docs/tasks/phase1-check.md` のように、Claude に書いてもらえます
